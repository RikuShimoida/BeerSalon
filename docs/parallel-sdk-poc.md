# /parallel 司令塔ロジックの SDK 化 — 比較評価と移行判断（Issue #373）

`/parallel`（複数 Issue を worktree 分離で並列実装する司令塔バッチ）は現在 **自然言語スキル**
（`.claude/skills/parallel/SKILL.md`）として記述されている。これを **Claude Agent SDK（TypeScript）で
手続き的なコード**として再実装できるかを検証し、制御性・保守性を比較する。

PoC 本体は `tools/parallel-sdk-poc/`。本ドキュメントはその比較評価と、本格移行するか否かの判断材料をまとめる。

> 本 Issue は調査止まり。本格移行するかは本 PoC の結果（＝本ドキュメント）を見てから別途判断する。

---

## 0. 前提: /parallel 司令塔ロジックの実体

現状スキル版は 4 フェーズ構成（`docs/worktree-workflow.md` が制約の根拠）:

| フェーズ | 内容 | 制約の根っこ |
|---|---|---|
| Phase 0 適格判定 | 各 Issue が DB スキーマ変更を含むか判定し、含むものは並列禁止で直列化 | 全 worktree が単一物理 DB（54422 postgres）を共有 |
| Phase 1 並列実装 | 適格 Issue ごとに実装エージェントを同時起動し、worktree 作成〜実装〜UT を並列 | UT は共有 DB に触らないので並列可 |
| Phase 2 IT/E2E 直列キュー | 共有 DB 依存テストを 1 体ずつ直列消化 | 共有 DB＋固定ポート競合で並列は非決定的 |
| Phase 3 コミット・PR・後片付け | worktree ごとに PR 作成 → 撤去 | — |

これらのうち **「判断・制御・集約」部分は本来コードで決定論的に書ける**。それを検証したのが本 PoC。

## 1. PoC で実際にコード化した「決定論部分」

| 決定論部分 | スキル版での扱い | PoC のコード | UT |
|---|---|---|---|
| Phase 0 適格判定（スキーマ変更を含むか） | Claude の自然言語判断 | `src/eligibility.ts` の `classifyIssue` / `classifyBatch`（正規表現シグナル・ラベル優先・矛盾検出・判断不能時の要確認フラグ） | ✓ 12 件 |
| 並列 vs 直列の実行制御 | 「1 メッセージでまとめて起動」「1 体ずつ」の口頭指示 | `src/orchestrator.ts`：並列は `Promise.all`、直列は `for-of await`。**コード構造そのもの**で並行/逐次を強制 | ✓（トレースで並行数を観測） |
| リトライ制御 | スキルに明示的な規定なし | `runImplementationWithRetry`：失敗時に決定論的な回数だけ再試行（自然言語版に無い付加価値） | ✓ 3 件 |
| 共有 DB 依存テストの直列キュー | 「qa-engineer を 1 体ずつ」の口頭指示 | `orchestrator.ts` で `for-of await`。成功実装かつ要求ありのものだけをキューに積む | ✓ 4 件 |
| 結果集約レポート | Claude の自由記述 | `src/report.ts` の `renderReport`：同じ入力なら常に同じレポート（差分比較可能） | ✓ 6 件 |
| 推測実装の抑止 | CLAUDE.md ルールを Claude が守る前提 | 判断不能な Issue を `needsHumanConfirmation` で自動処理から除外し人間に返す | ✓ |

**設計の肝**: `AgentRunner` インターフェース（`src/types.ts`）で「決定論ロジック」と「SDK 呼び出し」を分離。
dry-run では `MockAgentRunner`、本番では `createSdkRunner()`（`query()` を叩く）を差し込む。差し替え点が 1 箇所なので、
決定論部分を SDK から完全に切り離して UT できる。

### dry-run 実演で観測できたこと（`pnpm poc` のトレース）

```
impl-start #401 attempt=1 concurrentImpl=1
impl-start #402 attempt=1 concurrentImpl=2   ← 並列レーンが同時起動（Promise.all）
impl-end   #401 attempt=1
impl-end   #402 attempt=1
impl-start #401 attempt=2 concurrentImpl=1   ← #401 はリトライ（1 回目失敗 → 2 回目成功）
...
impl-start #403 attempt=1 concurrentImpl=1   ← 直列レーンは単独逐次
shared-start #402 / shared-end #402          ← 共有 DB テストを 1 件ずつ直列消化
shared-start #403 / shared-end #403
```

Phase 0 で「判断不能」と判定した #404 は自動処理から除外され、レポートの「人間確認待ち」に載る。

## 2. SDK 側の技術的成立性（確認済み）

`@anthropic-ai/claude-agent-sdk`（検証時 `0.1.77`）で以下が成立することを確認した:

- `query({ prompt, options })` は `AsyncGenerator`。`for await` でメッセージを消費し、`type === "result"` で最終結果を取得。
- `options.agents`（`Record<string, AgentDefinition>`）でサブエージェント（frontend-engineer / qa-engineer 相当）を定義でき、
  `allowedTools` に `Agent` を含めると起動できる。→ **スキル版のサブエージェント委譲を SDK 上で再現可能**。
- `options.cwd` で各 `query()` の作業ディレクトリを分離できる。→ **worktree ごとに cwd を固定すれば、SDK 上でファイル分離が成立**（Issue の「worktree 分離との組み合わせが SDK 上で成立するか」への回答＝**成立する**）。
- 複数 `query()` を `Promise.all` で並列実行できる。→ **並列実装フェーズを SDK で表現可能**。
- `hooks`（PreToolUse/PostToolUse 等）でツール実行をブロック・ログできる。→ スキーマ変更ロックや監査に応用可能。

型検査（`pnpm typecheck`）で `sdk-runner.ts` が実 SDK の型（`AgentDefinition` / `Options`）に通ることも確認済み。

## 3. 自然言語スキル版 vs SDK 版 — メリット/デメリット

### SDK 版（手続き的コード）のメリット

| 観点 | 内容 |
|---|---|
| **再現性** | 同じ入力なら常に同じ振り分け・同じレポート。適格判定を LLM の判断に委ねないので、実行ごとにブレない。 |
| **テスト可能性** | 決定論部分（振り分け・リトライ・集約）を UT で担保できる（PoC で 30 件）。スキル版は「意図どおり動いたか」を実行のたびに目視するしかない。 |
| **制御の明示性** | 並列/直列が `Promise.all` / `for-of await` という**コード構造**で強制される。「1 体ずつ」を Claude が守り忘れる余地がない。 |
| **リトライ・エラーハンドリング** | 失敗時の再試行回数・失敗の握り方をコードで規定できる。スキル版には明示的な規定がない。 |
| **監査可能性** | 判定理由（`reasons`）を構造化して残せる。なぜ serial にしたかが機械可読で追える。 |
| **回帰防止** | ロジック変更時に UT が壊れて気づける。スキル版は文面変更の影響を実行するまで確認できない。 |

### SDK 版のデメリット

| 観点 | 内容 |
|---|---|
| **保守コスト（二重メンテ）** | `/impl` 本体のフロー（前提チェック・環境コピー・PR 作成・後片付け）は依然スキルにある。SDK 版はそれを**別言語で再実装**することになり、スキルとコードの二重メンテが発生する。 |
| **柔軟性の喪失** | 適格判定を正規表現シグナルに固定すると、スキル版が持つ「文脈を読んで柔軟に判断する」力を失う。PoC でも判断不能ケースは人間確認に倒すしかなかった（＝完全自動化はできない）。 |
| **依存の増加** | `@anthropic-ai/claude-agent-sdk` への依存が増える。SDK の破壊的変更に追従するコストが生じる（検証時 0.1.x で、まだ API が動きうるバージョン帯）。 |
| **実行環境の分離コスト** | 独立 workspace（`pnpm-workspace.yaml` 分離）にしないと親モノレポへ依存が混入する。PoC でも実際にこの問題に当たり、境界を切って回避した。 |
| **起動オーバーヘッド** | 現状スキル版は Claude Code のメイン会話がそのまま司令塔になる。SDK 版は別プロセスで `query()` を起動するため、二重に Claude を走らせる構図になりうる。 |

## 4. 本格移行の判断材料

### 移行が「割に合う」条件

- 並列バッチを**高頻度**で回し、実行ごとの振り分けブレ・「1 体ずつ」の守り忘れが実害になっている。
- 適格判定を**ラベル運用**（`db-schema` 等）に寄せられ、正規表現シグナルで十分カバーできる。
- リトライ・監査ログなど、スキル版に無い制御を強く求めている。

### 移行が「割に合わない」条件（現状はこちら寄り）

- 個人開発で並列バッチの実行頻度が低い（`docs/worktree-workflow.md` §0 が「重い独立タスクが同時に複数ある場面以外は
  worktree 自体が割に合わない」と明記している。SDK 化はその上にさらにコストを乗せる）。
- `/impl` 本体がスキルにあるため、司令塔だけ SDK 化しても**二重メンテ**が残る。
- 適格判定の「文脈読み」をコードに固定すると、かえって融通が利かなくなる（判断不能→人間確認が増える）。
- **サブエージェント結果の受け取りが脆い**: PoC の `sdk-runner.ts` は `query()` の result テキストを正規表現
  （`/green|passed/i` 等）で判定しているが、これは LLM の自由記述に依存するため文言が変わると誤判定する。
  本格採用時は `AgentRunner` の返り値を SDK の構造化出力（JSON スキーマ）で受ける形に置き換える必要があり、
  ここを疎かにすると「決定論化したはずが結果判定が非決定的」という本末転倒に陥る。移行時の最優先改修点。

### 推奨（この PoC を踏まえて）

**現時点では本格移行しない。** ただし本 PoC で得た「決定論部分をコード化する」発想は有効なので、以下を候補として残す:

1. **部分採用**: 最も旨味が大きい「適格判定（Phase 0）」だけをコード化し、スキルから呼ぶハイブリッドは検討価値がある
   （振り分けのブレだけを消し、実装フロー本体はスキルに残す）。
2. **横展開候補**: 同種の「自然言語オーケストレーション」を持つ `/loop-issues`（「pr-review Low 以下 + E2E green + CI green の
   4 条件で自動マージ」という**条件判定**）は、決定論化の旨味が `/parallel` より大きい。移行するならこちらを先に別 Issue で検討する。
3. **再評価トリガー**: 並列バッチの実行頻度が上がる、または SDK が安定版（1.x）に達したタイミングで本評価を再実行する。
