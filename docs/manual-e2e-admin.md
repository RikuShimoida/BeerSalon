# 手動E2Eテストシナリオ - BeerSalonAdmin（管理画面）

管理画面（apps/admin）の手動動作確認用チェックリスト。3つの専門観点（ドメイン / アーキテクチャ / QA）を画面単位に統合した。

- **凡例**
  - `[D]` ドメインルール観点
  - `[A]` アーキテクチャ・セキュリティ・非機能観点
  - `[Q]` UI/UX・バリデーション・エッジケース観点
  - ⚠️ 仕様不備・設計不備の指摘
  - ❓ 仕様確認が必要な事項

- **根拠ドキュメント**: `routing.md §3` / `wireframe-admin.md` / `database.md §8` / `.claude/rules/admin.md` / `.claude/rules/supabase.md`
- **対象環境**: ローカル `http://localhost:3001`（apps/admin）
- **認証**: カスタムJWT認証（jose + bcryptjs）。**Supabase Auth は不使用**
- **権限**: `bar_owner`（自店舗のみ編集）/ `admin`（全店舗閲覧・店舗情報のみ編集、配下データは参照のみ）

---

## 0. テスト開始前のブロッカー（要件詳細の仕様不備）

手動E2Eを開始する前に **以下の仕様不備が解消されているか確認** すること。未解消だと「不具合か仕様か」の判定ができない項目が多発する。

### 🔴 ブロッカー（着手前に必ず解消）

- **B-1. メニュー登録フォームの仕様欠落（最重要）**
  - wireframe-admin.md §4-2 のビールメニュー登録に `beer_category_id`（NOT NULL）の入力欄がない → `beers` への INSERT 不可
  - `beers` がマスタか店舗ローカルか、既存ビールから選ぶ UI なのか毎回新規作成なのか未定義
  - 食事メニューの価格欄（`bar_food_menus.price`）が UI から欠落
  - wireframe「画像アップロード」 vs 実装「画像URL入力」の乖離

- **B-2. 権限境界違反のサーバ側検証が仕様化されていない**
  - bar_owner が他店舗データを操作できないことを、UIのボタン非表示やルーティング制御だけでなく **Server Action / API Route で JWT から `bar_id` を取得し、URLパラメータと突合する多層防御** で徹底する必要がある
  - database.md §8-1 で権限定義はあるが、実装層での検証方針が routing.md / .claude/rules/admin.md に未記載

- **B-3. 仕様ドキュメント（wireframe-admin.md）と実装の重大な乖離**
  - 市区町村: 仕様「テキストボックス」 vs 実装「静岡県内プルダウン」
  - ビールメニュー画像: 仕様「画像アップロード」 vs 実装「画像URL入力」
  - 記事 status: スキーマに draft/published/scheduled があるが UI に切替なし
  - → sync-docs で即時整合を取る必要

### 🟠 重要懸念（着手前に方針決定）

- **B-4. 店舗の論理削除・is_active 切替 UI の不在**
  - `bars.is_active` / `articles.deleted_at` / `admin_users.is_active` のカラムはあるが切替UIなし
  - 閉店店舗の非表示・誤投稿記事復旧などが運用で詰む可能性

- **B-5. Stripe連携の整合性設計不足**
  - `bar_subscriptions.status` 変化の画面反映、`cancel_at_period_end` の可視化、Webhook受信エンドポイント設計、未払い店舗の機能制限 が未定義

- **B-6. JWT有効期限・リフレッシュ戦略が未定義**
  - アクセストークン有効期限、リフレッシュトークン有無、強制ログアウト機構

- **B-7. 店舗削除・bar_manage_id 変更時の波及影響が未定義**
  - 店舗削除時に bar_subscriptions が連動キャンセルされない → 課金継続事故リスク
  - bar_manage_id 変更時のJWT再発行・既存セッション無効化が未定義

- **B-8. 画像アップロードとXSSの防御戦略が全画面で未定義**
  - MIME検証、サイズ上限、拡張子whitelist、Storage孤立ファイル掃除
  - `articles.body` がリッチテキスト/Markdown/プレーンか未定義

- **B-9. クライアント側バリデーションの抜け**
  - CouponForm: 割引値マイナス・%>100、開始>終了の未チェック
  - EventForm: 開始>終了の未チェック、画像5MBクライアント側未適用
  - ArticleCreateForm: 画像形式/サイズチェック未実装

- **B-10. 店舗登録 admin_users.name の入力欄なし**
  - database.md §8-1 で `name NOT NULL` だが wireframe-admin.md §3-1 Phase 1 に該当項目なし
  - 店舗名で代用するのか、登録者氏名なのか不明

- **B-11. `bars.latitude / longitude` の入力 UI なし**
  - 住所からのジオコーディングが自動か手動か未定義
  - ユーザー画面の Google Maps 表示と直結するため重要

- **B-12. パスワード強度ポリシーがユーザー画面と乖離**
  - ユーザー画面: 英大小文字＋数字＋記号
  - 管理画面: 8文字以上のみ。スタッフ共有IDとしては弱すぎる

### 🟡 確認推奨（テストしながら判断可）

- B-13. 廃止ルート（routing.md §3-9: /, /admin/master/*, /admin/users/*, /billing）の残置確認
- B-14. ページネーション仕様が全一覧画面で未定義
- B-15. ログイン試行のレート制限・アカウントロック
- B-16. 削除がハード削除か論理削除か（メニュー/クーポン/イベント）
- B-17. 同時編集時の競合解決（楽観ロック/後勝ち）
- B-18. 廃止記事復旧 UI（deleted_at 復元）
- B-19. 管理画面と user 画面の Cookie 衝突（同一ホスト・ポート違い）

## 付録: 観点別の重要懸念まとめ

### ドメインエキスパート観点 TOP3

1. **メニュー登録フォームの仕様欠落**（B-1: `beer_category_id` 不在、`beers` 運用方針未定義、食事価格欄なし）
2. **店舗の論理削除・is_active 切替 UI の不在**（B-4: 閉店店舗の非表示・誤投稿記事復旧などが運用で詰む）
3. **Stripe 連携の整合性設計不足**（B-5: status 反映、cancel_at_period_end 可視化、Webhook 設計）

### システムアーキテクト観点 TOP3

1. **権限境界違反のサーバ側検証が仕様化されていない**（B-2: Server Action の JWT 検証多層防御）
2. **店舗削除・bar_manage_id 変更時の波及影響が完全に未定義**（B-7: Stripe 課金継続事故、JWT再発行）
3. **画像アップロードとXSSの防御戦略が全画面で未定義**（B-8: MIME検証、XSS、`articles.body` フォーマット）

### QAエンジニア観点 TOP3

1. **クライアント側バリデーションの抜け**（B-9: クーポン/イベント/記事の入力境界）
2. **仕様ドキュメントと実装の重大な乖離**（B-3: 市区町村、ビール画像、記事status）
3. **認可・セッション境界のリグレッション**（B-2 と重複: API レベル拒否、店舗ID変更時セッション、同時ログイン）
